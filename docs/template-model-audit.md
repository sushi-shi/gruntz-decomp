# Template-origin audit

The consolidated PR #79 now includes the #80/#81 follow-ups and separates the
shared headers by library ownership. See [shared template ownership](template-header-ownership.md)
for the current public-header map, reproducible controls, and remaining questions.
Measurements below describe their named historical build stages, not the final
integrated-main snapshot.

The audit starts at merged main `814e76985`, after naming/padding PR #77 and
SDK-layout PR #78. It examines project-defined container-like records that may
actually be instantiations of an existing template. The initial identity audit is followed below by a compiled application of the
confirmed findings and a later usage-backed compiler-method application. The latest results are at the end of this document.

Run `nix develop -c python3 scripts/audit-template-models.py`. The script reads
the real compilation database with pylibclang, visits template bodies, records
base classes, methods and member offsets, and parses otherwise uncovered
source/header files. The complete record and template-declaration catalogs are
written under `build/audits/template-models/`, alongside the candidate worklist.

The original run covers 282 translation units, 1,853 record definitions, 443 owned
records and 20 template declarations visible in their ASTs. It identifies 94
review candidates with zero parse errors or uncovered files. Every candidate
has a disposition in [template-model-review.tsv](template-model-review.tsv).
These totals count definitions and declarations, not every implicit template
instantiation generated by the compiler.

### `CTypeCollRuntime`: restore a complete `zDArray<CString>` family

The exact surviving source is `LT2/lithshared/incs/ztools.h`, commit
`dfbe22fb4cc01bf7e5f54a79174fa8f108dd2f54`, blob
`8f548108894313b5b62d5cb6b17e6f078128cbd1`, in the
[original NOLF release](https://github.com/osgcc/no-one-lives-forever/blob/dfbe22fb4cc01bf7e5f54a79174fa8f108dd2f54/LT2/lithshared/incs/ztools.h).
The downloaded audit copy has the same Git blob hash as the lineage ledger.

Its `zDArray<T>` family at lines 1646–1697 explains all of the following facts
together:

* The constructor passes `sizeof(T)`, the two bounds, and overflow sentinel 1
  to `_zdvec`, then constructs `initcount` elements starting at `init`.
* The destructor destroys `hi - lo + 1` elements starting at `vec`.
* `operator[]` gets a slot through the erased dynamic-vector base, constructs
  newly allocated elements, and returns `T&`.
* The retail global initializer at 0x16e730 uses bounds 2000 and 2010 and calls
  CString construction. The deleting destructor at 0x16ea20 destroys the same
  four-byte elements before base teardown.
* Retail 0x310f0 reads the initialization pointer/count at +0x1c/+0x20, calls
  `CString::CString` at 0x1b9b93 and advances four bytes. It is typed element
  initialization, then misattributed to generic `_zdvec::IndexToPtr`.

The original introduction, commit `93d36c1bd`, already described
`CTypeCollRuntime` as a `zDArray<CString>` collection, but declared a separately
named class and synthetic vtable identity. Later work reconstructed its bodies
without removing that duplicate source identity. This is the same failure mode
as the removed SDK substitutes: a matching implementation does not establish
the invented class name.

The correction includes the existing `zDArray<CActHandler>` family: generic
constructor/destructor/indexing bodies now own typed element construction,
and `g_typeColl` uses the string specialization.
The existing `ResolveEntry` and `ResolveEntryCallReport` bodies are hand-expanded
variants of the source's erased `get` plus typed indexing boundary; they need
review as one family, including all registrars and static initializers.

There is also a concrete inheritance repair. The surviving `_zvec` ends with
the stride field, while `_zdvec` adds `init` and `initcount`. Retail 0x16dda0
writes +0x1c and +0x20 after the base constructor. Move the corresponding
`m_alloc`/`m_grown` fields and the dynamic reallocation operation out of the
pre-audit `_zvec` model. Preserve the complete derived size and verified offsets.
The source-facing return is a reference; identical pointer/reference machine
returns do not justify keeping a pointer-only API.

### `CButeTree`: usage selects `zSymTab<i32>`

The same surviving header declares a fieldless `zSymTab<T>` derived from
`zPTree`, forwarding typed insert/lookup/add calls and binding a typed teardown
adapter. The current `CButeTree` has the same erased forwarding surface,
passive cleanup, and an independently emitted one-byte no-op callback at
0x16ea10. Its global stores action IDs as pointer-sized payloads.

The complete producer/consumer family selects an integer interpretation:
`g_typeCounter` starts at 2000, each insertion stores that counter's value,
and registration increments it. Lookup results are tested against zero, used
as array indices, and stored as integer event codes. The payloads are never
dereferenced as objects. The existing CButeMgr symbol table already uses real
`zSymTab<CButeMgr::CSymTabItem>` and is a positive control for the family.

The prior audit over-weighted the fact that several scalar/pointer arguments
emit identical code. That compiler control limits recovery of the exact original
declaration; it does not defeat the usage-backed `i32` reconstruction. The
follow-up replaces `CButeTree` and its separate no-op callback with the shared
`zSymTab<i32>` specialization. Passive cleanup, pointer-encoded ID storage,
the global owner, and its complete base layout remain the retail operations.
The adoption decision is `nolf-zsymtab-action-ids` in the lineage ledger.

### Arrays, pools and lists needing more evidence

`CFixedPtrArray32` stores 32 pointers inline. Its complete 0x134be0/0x134c60/
0x134c80 family does not have the heap-backed storage of MFC `CArray` or the
surviving Lith `CMoArray<T,C>`. Its fieldless `CInputDeviceGroup` wrapper belongs
in the same identity investigation. A hardcoded capacity and one element type
do not recover a primary template or a non-type template parameter.

`FreeNodePool`, `CBrickzNodePool` and `CBrickzCellNodePool` are plausible generic
pool families. The two Brickz allocation bodies differ in node-link semantics,
field roles and clearing of the cell's search pointer. A valid shared template
would need the real node helper/trait contract; merely parameterizing the
existing arithmetic would invent that contract.

`BucketHead`, `SoundSampleList`, `SoundBufferInstanceList` and `SoundTaskList`
have little state beyond `CLTBaseList`. Both the non-template `CLTBaseList` and
the later typed `CLithBaseList<T>` survive in the pinned Lith source. Resolve
node inheritance and the complete call family before choosing between them.
Sound-task filtering is extra domain behavior that must retain an owner even
if its list base proves to be a template.

## Controls and scope limits

The already restored four explicit MFC `CArray` definitions and the existing
`zDArray`/`zSymTab` declarations are controls, not new duplicate findings.
The retail RTTI string census finds two template type descriptors:
`zDArray<int (CUserLogic::*)()>` and the playlist `CArray`. Other modules lack
that RTTI coverage, so absence of a descriptor is not negative type evidence.

The pinned `libs/lith/baselist.h`, `virtlist.h`, `basehash.h` and Rez owner
headers preserve concrete non-template declarations. Several fieldless derived
Rez lists and hash tables really were authored classes. Replacing them just
because a template could have the same layout would undo the source recovery.
Their existing lineage-ledger decisions remain authoritative.

The worklist combines collection names, template base relationships, fieldless
collection subclasses, complete instantiated-layout candidates and storage
signals. These intentionally broad signals require review; a shared `CObject`
base or count/pointer member pair alone does not establish a template identity.
Unknown layouts and erased call boundaries cannot be proven clean merely by
the census. The unresolved rows remain explicit investigation items.

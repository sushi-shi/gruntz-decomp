# Template-origin audit

The audit starts at merged main `814e76985`, after naming/padding PR #77 and
SDK-layout PR #78. It examines project-defined container-like records that may
actually be instantiations of an existing template. The initial identity audit is followed below by a compiled application of the
confirmed findings; unresolved identities have not been replaced.

Run `nix develop -c python3 scripts/audit-template-models.py`. The script reads
the real compilation database with pylibclang, visits template bodies, records
base classes, methods and member offsets, and parses otherwise uncovered
source/header files. The complete record and template-declaration catalogs are
written under `build/audits/template-models/`, alongside the candidate worklist.

The original run covers 282 translation units, 1,853 record definitions, 443 owned
records and 20 template declarations visible in their ASTs. It identifies 94
review candidates with zero parse errors or uncovered files. Every candidate
has a disposition in [template-model-review.tsv](template-model-review.tsv).
These totals count definitions and declarations, not every implicit template
instantiation generated by the compiler.

### `CTypeCollRuntime`: restore a complete `zDArray<CString>` family

The exact surviving source is `LT2/lithshared/incs/ztools.h`, commit
`dfbe22fb4cc01bf7e5f54a79174fa8f108dd2f54`, blob
`8f548108894313b5b62d5cb6b17e6f078128cbd1`, in the
[original NOLF release](https://github.com/osgcc/no-one-lives-forever/blob/dfbe22fb4cc01bf7e5f54a79174fa8f108dd2f54/LT2/lithshared/incs/ztools.h).
The downloaded audit copy has the same Git blob hash as the lineage ledger.

Its `zDArray<T>` family at lines 1646–1697 explains all of the following facts
together:

* The constructor passes `sizeof(T)`, the two bounds, and overflow sentinel 1
  to `_zdvec`, then constructs `initcount` elements starting at `init`.
* The destructor destroys `hi - lo + 1` elements starting at `vec`.
* `operator[]` gets a slot through the erased dynamic-vector base, constructs
  newly allocated elements, and returns `T&`.
* The retail global initializer at 0x16e730 uses bounds 2000 and 2010 and calls
  CString construction. The deleting destructor at 0x16ea20 destroys the same
  four-byte elements before base teardown.
* Retail 0x310f0 reads the initialization pointer/count at +0x1c/+0x20, calls
  `CString::CString` at 0x1b9b93 and advances four bytes. It is typed element
  initialization, then misattributed to generic `_zdvec::IndexToPtr`.

The original introduction, commit `93d36c1bd`, already described
`CTypeCollRuntime` as a `zDArray<CString>` collection, but declared a separately
named class and synthetic vtable identity. Later work reconstructed its bodies
without removing that duplicate source identity. This is the same failure mode
as the removed SDK substitutes: a matching implementation does not establish
the invented class name.

The correction includes the existing `zDArray<CActHandler>` family: generic
constructor/destructor/indexing bodies now own typed element construction,
and `g_typeColl` uses the string specialization.
The existing `ResolveEntry` and `ResolveEntryCallReport` bodies are hand-expanded
variants of the source's erased `get` plus typed indexing boundary; they need
review as one family, including all registrars and static initializers.

There is also a concrete inheritance repair. The surviving `_zvec` ends with
the stride field, while `_zdvec` adds `init` and `initcount`. Retail 0x16dda0
writes +0x1c and +0x20 after the base constructor. Move the corresponding
`m_alloc`/`m_grown` fields and the dynamic reallocation operation out of the
pre-audit `_zvec` model. Preserve the complete derived size and verified offsets.
The source-facing return is a reference; identical pointer/reference machine
returns do not justify keeping a pointer-only API.

### `CButeTree`: the family is stronger than the argument identity

The same surviving header declares a fieldless `zSymTab<T>` derived from
`zPTree`, forwarding typed insert/lookup/add calls and binding a typed teardown
adapter. The current `CButeTree` has the same erased forwarding surface,
passive cleanup, and an independently emitted one-byte no-op callback at
0x16ea10. Its global stores action IDs as pointer-sized payloads.

These facts support the template family, but do not select `T`: multiple scalar
or pointer instantiations have the same no-op pseudo-destructor and erased
payload operations. Do not replace the class with a guessed specialization.
The next evidence should be a surviving original declaration, a relevant debug
type/instantiation record, or an unambiguous typed use. Generated labels are not
independent evidence. The existing CButeMgr symbol table already uses real
`zSymTab<CButeMgr::CSymTabItem>` and is a positive control.

### Arrays, pools and lists needing more evidence

`CFixedPtrArray32` stores 32 pointers inline. Its complete 0x134be0/0x134c60/
0x134c80 family does not have the heap-backed storage of MFC `CArray` or the
surviving Lith `CMoArray<T,C>`. Its fieldless `CInputDeviceGroup` wrapper belongs
in the same identity investigation. A hardcoded capacity and one element type
do not recover a primary template or a non-type template parameter.

`FreeNodePool`, `CBrickzNodePool` and `CBrickzCellNodePool` are plausible generic
pool families. The two Brickz allocation bodies differ in node-link semantics,
field roles and clearing of the cell's search pointer. A valid shared template
would need the real node helper/trait contract; merely parameterizing the
existing arithmetic would invent that contract.

`BucketHead`, `SoundSampleList`, `SoundBufferInstanceList` and `SoundTaskList`
have little state beyond `CLTBaseList`. Both the non-template `CLTBaseList` and
the later typed `CLithBaseList<T>` survive in the pinned Lith source. Resolve
node inheritance and the complete call family before choosing between them.
Sound-task filtering is extra domain behavior that must retain an owner even
if its list base proves to be a template.

## Controls and scope limits

The already restored four explicit MFC `CArray` definitions and the existing
`zDArray`/`zSymTab` declarations are controls, not new duplicate findings.
The retail RTTI string census finds two template type descriptors:
`zDArray<int (CUserLogic::*)()>` and the playlist `CArray`. Other modules lack
that RTTI coverage, so absence of a descriptor is not negative type evidence.

The pinned `libs/lith/baselist.h`, `virtlist.h`, `basehash.h` and Rez owner
headers preserve concrete non-template declarations. Several fieldless derived
Rez lists and hash tables really were authored classes. Replacing them just
because a template could have the same layout would undo the source recovery.
Their existing lineage-ledger decisions remain authoritative.

The worklist combines collection names, template base relationships, fieldless
collection subclasses, complete instantiated-layout candidates and storage
signals. These intentionally broad signals require review; a shared `CObject`
base or count/pointer member pair alone does not establish a template identity.
Unknown layouts and erased call boundaries cannot be proven clean merely by
the census. The unresolved rows remain explicit investigation items.

## Compiled application

`CTypeCollRuntime` and its header are removed. `g_typeColl` now has the real
`zDArray<CString>` type and specialized vtable identity. Both string and handler
arrays use shared constructor/destructor and reference-returning index bodies.
`_zdvec` owns erased dynamic access, growth, and the two initialization fields;
`_zvec` ends at the stride. Source-specific adaptations and remaining caller
factoring are recorded only in `nolf-zdarray-*` in the lineage ledger.

The controlled comparison starts at audit commit `0682771b3`, whose C++ is
merged main `814e76985`. Every stage compiles real VC5 objects; the target code
denominator remains 1,167,465 bytes / 7,466 report functions.

| State | Overall current fuzzy | Change from start |
| --- | ---: | ---: |
| Before | 95.75678% | — |
| Confirmed owners and real CString type, existing call cuts | 95.67601% | -0.08077 pp |
| Shared generic lifetime bodies for both element types | 95.66925% | -0.08753 pp |
| Shared generic indexing and visible erased inline helper | 94.69956% | -1.05722 pp |

Both typed index bodies (0x310f0 and 0x464e0), the erased accessor (0x312a0),
all base constructors/destructors, handler-array lifetime functions, and the
string-array deleting destructor remain 100%. Growth at 0x16da80 remains
91.8584%, its previous current and historical score. The table does not count
unpaired dynamic-initializer helpers as report functions. Their actual code
was checked separately: the 81-byte initializer at 0x16e730 and 72-byte teardown
at 0x16e7a0 match retail byte-for-byte after resolving every ordered relocation.

The aggregate hides large local changes: `RegisterGruntActions` moves from
100% to 8.303815%, `RegisterWarlordActions` from 100% to 23.621399%, and
`StepRowUnits` from 83.512184% to 41.490196%. These caller residues are open,
not certified source closures.

The registrar's direct cause is specifically the newly header-visible ordinary
`_zdvec::IndexToPtr`, not the separate unmarked-template compiler exception.
It loses 20 of retail's 35 accessor calls and gains 20 calls each to `GrowTo`,
`GetRetAddr`, and `CVariantSlot::Set`. The raw accessor expands bounds, growth,
and error handling into the repeated registration sites. The registrar grows
from retail's 0x9e5 bytes / 113 calls / 73 branches to 0x12eb bytes / 153 calls /
173 branches. Registers already differ at +0x13; the first structural change is
retail's accessor-call block at +0x7a becoming the expanded block at base +0x82.
The ordered referent comparison identifies 20 replacement regions with that
same helper topology. This establishes the codegen cause of the drop without
rejecting the recovered container identity or certifying the caller factoring.
The stale bounded review for `RouteToNearbyEnemy` is reopened because its
call/relocation census changes from 26/37 to 33/67. Historical MAX is retained.

A separate `/Ob1` versus `/Ob0` compiler control proves that an out-of-class,
unmarked template member can expand under VC5 `/Ob1`; the equivalent ordinary
member stays a call. The old blanket candidacy rule is corrected in the model,
skill, and [reusable pattern](patterns/vc5-template-members-inline-without-inline-keyword.md).

The follow-up AST census still parses all 282 TUs without errors or uncovered
files. It has 93 current candidates; the 94 review rows include one explicit
removed-candidate row for `CTypeCollRuntime`. `_zvec` measures 28 bytes,
`_zdvec` 36, with derived fields at +0x1c/+0x20. The confirmed correction does
not establish `CButeTree`'s argument or a primary template for the other nine.

Further raw list evidence supports retaining their erased base: sound, grid,
and Rez callers share `CLTBaseList::InsertFirst` at 0x1390e0. The sound ramp
caller adjusts its polymorphic node by +4 before that call. The surviving
`CLithBaseList<T>` instead supplies its own typed-link class; replacing these
wrappers with it would require new evidence, not just equal first/last storage.

Artifacts under `build/audits/template-application/` retain the baseline,
stage reports, core disassembly, caller delta, fresh census, and actual compiler
controls. Final `gruntz build` passes MAX and all fast/normal gates. All 4,429 historical
RVA maxima are preserved. Eight focused verifier controls and the inline-model
selftests pass; a standalone VC5 compile verifies both headers and the base/
derived sizes and offsets. The optional whole-lineage validator also reports
30 pre-existing metadata findings, outside the three new adoption rows; these
are not hidden by the successful build gates.

## Reassessment of the ten remaining records

The hypothesis that all ten have a template origin remains open. The audit's
unresolved dispositions do not certify the current names as authored concrete
classes. Exact original names are not a prerequisite for reconstruction:
independent layout, ownership, typed-use, and complete-family agreement can
establish an instantiation. The remaining issue is selecting a model that those
facts actually distinguish from its alternatives.

| Records | Positive evidence | What the follow-up establishes |
| --- | --- | --- |
| `CButeTree` | Complete fieldless `zPTree` wrapper and teardown-adapter family strongly support `zSymTab<T>`. | A real VC5 control using the existing shared header instantiates `i32`, `char`, and `void*`. All three have the current wrapper's complete size, emit a one-byte `ret` teardown adapter, and forward lookup to the same erased callee. The family is strong; these operations do not select the argument. |
| `CFixedPtrArray32`, `CInputDeviceGroup` | Complete 32-element inline pointer storage and typed input-device consumers. | The array/group relationship could hide a template or an embedded template member. `CLithSimpAryStat<CInputDevBase*,32>` explains the slots but lacks the group's two dwords and append/count API. `CFastMoArray<T>` is heap-backed. Neither is a demonstrated replacement for the complete owner. |
| `FreeNodePool` | Typed contiguous allocation, a free chain, and a configurable payload offset are generic-pool evidence. | The surviving `ObjectBank<T>` uses a larger paged `StructBank`, and `CObjectBank<T>` allocates individual objects through a counted linked list. Neither explains this 16-byte, single-block owner. A different primary template remains possible. |
| `CBrickzNodePool`, `CBrickzCellNodePool` | Closely parallel complete allocation/linking/free families support investigating shared generic origin. | The allocation and teardown instructions independently prove reversed ownership fields: node storage is +4, cell storage is +0. The extra cell search-pointer store is also real. One unchanged primary template cannot explain both layouts; separate templates, specializations, or another owner layer remain possible. |
| `BucketHead`, `SoundSampleList`, `SoundBufferInstanceList`, `SoundTaskList` | Repeated fieldless wrappers around the same intrusive list are plausible typed adapters. | The shared erased insert/delete callees and base-subobject pointers are real. They rule out directly substituting the surviving typed-link `CLithBaseList<T>` implementation, but do not rule out an earlier template adapter over `CLTBaseList`. `SoundTaskList` also has buffer/tag filtering behavior whose owner must be recovered. |

The follow-up reads and Git-blob-verifies 17 headers from pinned `845119c`,
including Blood2's `FastArray`, `BareList`, `LinkList`, `MultiLinkList`,
`GoodLinkList`, `FastLinkList`, both object-bank families, and the corresponding
Lith/stdlith definitions. This broadens the source check beyond MFC and later
dynamic arrays. It finds no complete replacement for the remaining records.
The original NOLF release's complete tree was also checked for additional
array/list/pool headers. No claim is made that all possible source lineages
have been exhausted.

The new controls are under `build/audits/template-application/`: the seven raw
pool/array bodies, `symtab-argument-probe.*`, `symtab-argument-verdict.txt`,
`register-grunt-inline-model.txt`, `register-grunt-semdiff.txt`, and the verified
`oracles/` copies. These checks make no further production C++ changes.

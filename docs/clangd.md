# The clang-cl compilation database (clangd, `gruntz lsp`, extraction)

`build/clangd/compile_commands.json` is a **clang-cl** compilation database over
the reconstructed tree, generated by `python3 -m gruntz.graph.compdb`. It lets
clang-based tools parse `src/`, `include/` and the vendored sources against the
project's real **MSVC 5.0 / MFC 4.2 / DirectX 6** headers.

clang is only a **reader** of this MSVC5-dialect code. The Wine MSVC 5.0 build
(the ninja `cl` edge → `gruntz.tool.cl`) and objdiff remain the sole verdict on
correctness; clangd's diagnostics are not build truth.

## Why a separate database

The matching build compiles each unit with **MSVC 5.0's `CL.EXE` under Wine**.
clang cannot invoke that. So this database is maintained in **clang-cl driver
form**: it points clang at the toolchain's MSVC/MFC/DirectX headers and asks it
to *emulate* cl 11.00 (`_MSC_VER 1100`, hence
`-fms-compatibility-version=11.00`). clang reads those headers as plain files —
**no Wine, no `CL.EXE`** — parse-only, never a real compile.

## It is NOT optional editor tooling any more

Four consumers read it, and two of them are inside the build:

| consumer | what it needs the DB for |
| :-- | :-- |
| `gruntz.tool.clang` | the per-TU extraction flags behind `gruntz labels` — a unit with no entry silently falls back to bare MS flags, which is why generation always ends with a coverage check **through the consumer's own parser** |
| `gruntz.verify.fingerprints` | the per-function source extents the MAX ledger hashes |
| `gruntz.lsp` (`refs`/`hover`/`rename`) | the USR-exact source navigation and bulk member renamer |
| clangd itself | any editor's go-to-def / completion / hover / diagnostics, via the committed `.clangd` |

Because the label extraction depends on it, **`compdb` is a build edge**: the
ninja graph re-runs it whenever `config/units.toml` or the generator module
changes, and it writes if-changed so an unchanged payload does not bump the
mtime and re-run 300 downstream edges.

The one case ninja cannot see is a **toolchain bump**, which moves only
`$MSVC_DIR`/`$DXSDK_DIR`. After re-pinning, run
`python3 -m gruntz.graph.compdb` once by hand.

## What the generator emits

One clang-cl entry per unit, all sharing **one flag set**:

```
clang-cl /c <src> --target=i386-pc-windows-msvc \
  -fms-compatibility-version=11.00 -fms-extensions -fdelayed-template-parsing \
  /imsvc <mirror dirs> /imsvc <MSVC_DIR>/include /imsvc <DXSDK_DIR>/Include \
  /D_X86_ /DWIN32 /D_WINDOWS /D_MBCS
```

- **lowercase include mirrors.** The 1990s headers are ALL-UPPERCASE on disk
  (`STRING.H`, `AFXWIN.H`) but the sources include them lowercase, and clang on
  a case-sensitive filesystem cannot find them. The generator builds symlink
  mirrors under `build/clangd/inc-lower/` and puts them first, the real dirs
  after, **DX before MSVC** (VC5's own `DDRAW.H` is DirectX 3-era and would
  shadow the SDK's).
- **`/imsvc`** marks the toolchain headers as *system* includes, so diagnostics
  originating inside MFC/CRT/DirectX are suppressed — only our sources matter.
- **`_MBCS`**, and **not** `_AFXDLL`: we link static ANSI/MBCS MFC 4.2
  (`NAFXCW.LIB`), not the shared build, and not `_UNICODE`.
- **One flag set for every unit.** The manifest's `[flags]` profiles differ only
  in `/GX` and `/GR`, which change cl's EH tables and RTTI emission, not clang's
  parse. The uniform set is the state every extracted fragment was produced
  under.

## `.clangd`

The committed root `.clangd` points `CompilationDatabase` at `build/clangd/`,
mirrors the target / ms-compat / ms-extensions / delayed-template-parsing flags
globally (so they also apply when clangd opens a header with no direct compdb
entry), and adds **`-ferror-limit=0`**. That last one is essential: the
MSVC-dialect cascades in the MFC headers exceed clangd's default ~20-error
limit, which would **abort the parse mid-TU** and lose the AST below the abort
point. clangd's command mangler drops `-ferror-limit` when it comes from the
compdb, so it must live in `.clangd`. A few noisy clang-cl warnings
(`-Wmicrosoft`, pragma/pack, nonportable include path, writable strings) are
suppressed there too.

## Usage

```sh
nix develop                              # exports MSVC_DIR / DXSDK_DIR, ships clangd
gruntz build                             # regenerates the DB as part of the graph
python3 -m gruntz.graph.compdb           # or by hand (after a toolchain bump)
python3 -m gruntz.graph.compdb --check   # verify the existing file only
```

Then open the repo in any clangd-enabled editor; it reads `.clangd` and the
generated DB automatically. A one-off check from the CLI:

```sh
clangd --compile-commands-dir=build/clangd --check=vendor/zlib-1.0.4/adler32.c
```

A successful run ends with `All checks completed, 0 errors`.

## Caveats

- **MSVC5 emulation is best-effort.** clang's `-fms-compatibility` does not model
  every MSVC 5.0 dialect quirk in MFC 4.2. clangd recovers and still serves
  navigation and hover on a partially-erroring TU, but expect some spurious
  diagnostics in heavy MFC code. They do **not** reflect the real build.
- **Navigation is reliable, diagnostics are not.** Never take a clangd error as
  evidence about the match; compile with `gruntz build` and read objdiff.

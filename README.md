## Link status

Linking is **opt-in and out of the loop**: `gruntz build` does not link.
`gruntz link` (`ninja candidate`) produces `build/exe/GRUNTZ.candidate.EXE`
plus its `.map`, and `gruntz verify check --tier link` audits it:

- **link defects** — 0 unresolved externals, plus a pre-link closure over the
  base objects (an undefined external no base obj, toolchain `.LIB` or import
  supplies is a guaranteed `unresolved external symbol`);
- **section census** — the candidate's section table against retail's, per
  section (`gruntz verify link-tier --census`); a section retail has that the
  candidate lacks is fatal;
- **image diff** — for every function the compare report scores at 100%, the
  candidate's bytes at its *link-assigned* rva must equal retail's under
  relocation masking. That is the check per-object objdiff cannot make:
  final placement.

`.rsrc` is proven separately and completely from source — `gruntz rsrc check`
compiles `src/Gruntz/Gruntz.rc` with the era RC.EXE and byte-compares all 75
resources against the retail image (see [Resources](#resources)).

Size attribution and the region census are written up in
[`docs/image-diff.md`](docs/image-diff.md) and
[`https://github.com/sushi-shi/gruntz-decomp/blob/b27b05deb249e4cacbb29f55f17b469ecfe56f26/docs/link-section-audit.md`](https://github.com/sushi-shi/gruntz-decomp/blob/b27b05deb249e4cacbb29f55f17b469ecfe56f26/docs/link-section-audit.md).

## Requirements

Linux (x86_64) with [Nix](https://nixos.org/download) and flakes enabled
(`experimental-features = nix-command flakes`).

## Quickstart

From a fresh clone to a running match loop, four commands:

**1. Enter the dev shell.**

```sh
nix develop          # ONE shell: analysis tools + MSVC 5.0-under-Wine
```

One shell provides everything: `vostok-delinker`, `objdiff` / `objdiff-cli`,
`ghidra`, `llvm-pdbutil`, python/ripgrep/etc. **and** the MSVC 5.0 toolchain under
Wine. The flake fetches `GRUNTZ.EXE` (plus the `CLAW`/`MEDIEVAL` cross-diff siblings
and the VC5 toolchain) automatically and exports `$GRUNTZ_EXE`.

**2. Build the local environment (one-time; auto-run on shell entry).**

```sh
gruntz init          # the build Wine prefix; cheap after initial setup
```

`gruntz init` creates and verifies the Wine prefix. The clangd compilation database
is a build edge, not a setup step — `gruntz build` regenerates it whenever
`config/units.toml` or the generator changes. The build and delink never create or
read a Ghidra database; run `gruntz ghidra build` explicitly only when the optional
viewer is useful.

**3. Run the matching loop.**

```sh
gruntz match fader   # fast loop: compile, label, delink, compare ONE unit (~5s)
gruntz build         # everything: cl → labels → model → delink → compare
gruntz build verify  # + the MAX gate and gate tiers, when preparing a merge
```

This compiles the `src/` "base" objects (MSVC 5.0 under Wine), extracts the source
labels, resolves the Model, delinks the retail EXE into "target" objects, and
objdiffs them. The report lands at **`build/objdiff/compare-new/report.json`**.
`gruntz match <unit|source>` rebuilds only the named units, even after an edit to
a header other units include; `gruntz build` refreshes the rest. Gates are not
part of either: `gruntz build verify` runs the MAX gate plus the `fast` and
`normal` tiers before a merge. The heavier tiers are opt-in:

```sh
gruntz verify check --tier full   # binary-evidence audits (layouts, relocs, vtables,
                                  # the data access map + coverage census)
gruntz verify check --tier link   # candidate-EXE audits; needs `gruntz link` first
gruntz verify status              # the per-unit / per-function score table
```

**4. Navigate the code semantically.**

```sh
gruntz sema -h       # source/target navigator (xref, disasm, rva, class, strings, match)
```

Prefer `gruntz sema` over grep for any semantic question (who calls this, what type is
this member, which vtable slot). See
[`docs/build-system.md`](docs/build-system.md#semantic-navigation--gruntz-sema).

**Where to read next:** [documentation index](docs/README.md),
[`docs/build-system.md`](docs/build-system.md) (the pipeline), and
[`docs/tooling-map.md`](docs/tooling-map.md) (verbs → modules). Run
`gruntz verify status` for the live match state.

## Formatting

The reconstructed C++ follows a **Rust-like clang-format style** (root
`.clang-format`): 4-space indent, attached braces, `int* p`, braces on every
control body. It is **whitespace-only, so matching-neutral**. A tracked
pre-commit hook (`.githooks/pre-commit`, enabled by the dev shell) runs
`clang-format` over staged `src/`+`include/` files automatically; sweep the tree
by hand with `clang-format --style=file -i` over those two dirs.
**`vendor/` is kept verbatim and never formatted** (excluded by the hook and by
`vendor/.clang-format`). See
[`docs/build-system.md`](docs/build-system.md#formatting--the-rust-like-house-style).

## The pipeline

**Target side** — rebuilt only when source labels or the tracked retail inventory change:

```
GRUNTZ.EXE + config/retail/*.tsv + src/ labels
           → claims  (gruntz labels)  → the Model  (gruntz model → build/gen/bindings.tsv)
           → synthetic PDB  (gruntz.delink.pdb_synth: bindings + PE relocation targets)
           → vostok-delinker  → per-symbol COFF "target" objects
```

**The matching loop** — the only part that re-runs each `gruntz build`:

```
edit C++ in src/  →  compile "base" objs (MSVC 5.0 under Wine)
                  →  objdiff  (x86/COFF)  base  vs  the delinked "target" objs
                  →  iterate the C++ until each function matches byte-for-byte
```

## Resources

`.rsrc` is not extracted, it is **compiled from source**. `src/Gruntz/Gruntz.rc`
plus `src/Gruntz/res/*.{ico,cur}` is the single carrier of retail's 75 resources,
and the era `RC.EXE` (5.00.1472.1, bundled with the toolchain release) builds it:

```sh
gruntz rsrc check    # compile Gruntz.rc, byte-compare all 75 payloads vs retail
```

The check compares type, name, language, payload bytes and payload order against
the retail PE in both directions — no extracted resource bytes are stored anywhere,
the retail image is the only oracle.

## The Ghidra viewer

Ghidra is an optional viewer, not pipeline state, and the export is **one-way by
ruling**: matching works from `gruntz sema disasm` assembly, never from a decompile,
and nothing Ghidra produces flows back into delinking, matching or the gates.

```sh
gruntz ghidra -h         # build / update / status / verify RVA / export
```

There is one name authority: the **Model**. `gruntz ghidra export` flattens
`build/gen/bindings.tsv` plus `config/retail/link_bands.tsv` into a single
self-contained payload (`build/ghidra/knowledge.json`), which the Ghidra-side
script reads without importing this tree. Every census row is exported, claimed or
not — an unclaimed row is still a real object start with a derived extent, which
Ghidra's own carve does not have. Where Ghidra's auto-carve and the census
disagree, the census wins.
